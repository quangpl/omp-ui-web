# OMP-UI REST API (v1)

Base path: `/api/v1`. JSON in/out. Errors: HTTP 4xx/5xx with `{ "error": "message" }`.
Designed for the web UI and future mobile clients: a client only needs the **server URL** and a **username (or email) and password**.

## Authentication

| Method | Path | Body | Response | Auth |
| --- | --- | --- | --- | --- |
| GET | `/auth/status` | – | `AuthStatus`: `{ configured: boolean, authenticated: boolean, user: User \| null }`. `configured`: at least one account exists; `user`: the signed-in account | none |
| POST | `/auth/setup` | `{ username?, email?, password }` (`username` default `"admin"`; password min 8 chars) | `TokenResponse` + cookie. Creates the first account, an admin. 400 for an invalid username, email or password | none; only while no account exists (409 otherwise) |
| POST | `/auth/login` | `{ username?, password }` | `TokenResponse` + cookie. `username` is a username or an email (case-insensitive); omitted or empty → `"admin"` (password-only clients). 401 `{ error: "Invalid username or password" }` (also for a deactivated account); 409 before setup | none; rate limited (429 with `retry-after`) |
| POST | `/auth/logout` | – | `{ ok: true }`, clears cookie | any |
| POST | `/auth/password` | `{ current, next }` | `TokenResponse` for this session. Changes **the caller's** password and signs out the caller's other sessions and chat logins; other accounts are untouched. 403 wrong `current`, 400 `next` under 8 chars | required |

`TokenResponse` = `{ token, expiresAt, user: User }`. `User` = `{ id, username, email: string \| null, role: "admin" \| "user", isActive, createdAt, updatedAt }`.

Authenticated requests send **either** the `omp_ui_token` httpOnly cookie (web) **or** `Authorization: Bearer <token>` (mobile/CLI).
Tokens (format `v2`) are HMAC-SHA256 signed, valid 30 days and bound to one account: they stop working when that account's password changes (by itself, an admin or `omp-ui passwd`), or when it is deactivated, changes role or is deleted. Bumping the global epoch (settings key `token_epoch`) revokes every account's tokens at once. Tokens issued before the multi-user upgrade (v1) are rejected, so every client signs in once more.

Upgrades: the old admin password becomes the account `admin`, and every existing project, card and credential is assigned to the first admin at boot. The `ADMIN_PASSWORD` env var, when set, is applied at every boot to the `admin` account: created if missing, made an active admin, and signed out when the password differs from the stored one. `omp-ui passwd` writes `ADMIN_PASSWORD` to `.env`, so it resets the `admin` account only (at the next boot).

### Access control

Data is per user: a regular user (`role: "user"`) sees and changes only their own projects and everything under them (cards, comments, runs and run events, schedulers, artifacts, card and project files, workspaces, git actions), their own [credentials](#credentials), and only those in live events (`/events`), the agent queue (`/queue`) and the dashboard. New projects and credentials belong to their creator. Admins see and change everyone's data. An id the caller cannot see answers 404 exactly like an unknown one.

Admin only (403 `{ error: "Admin only" }` for regular users, recorded as a security event):

- every method: `/users/**`, `/terminal/**`, `/docker/**`, `/logs/**` except `POST /logs/access` (the page-view beacon), `/settings/cleanup`, `/settings/telemetry/test`, `/settings/ai-providers/oauth/**`, `/stats/maintenance`, `/mcp/sync`, `/mcp/:name/test`, `/chat/{telegram,discord}/{connect,disconnect}`.
- mutations only (GET stays open): `POST /system/restart`, `PATCH /settings`, `PUT /omp-config`, `PATCH /settings/ai-providers`, `POST /settings/ai-providers/test`, `POST /mcp`, `PATCH`/`DELETE /mcp/:name`.

For regular users `GET /omp-config` answers `raw: ""` and `version: ""` (the file may hold secrets).

Data directory: for regular users, `/fs/**`, `/git/init`, `/git/repo`, `/git/clone`, the project-files routes and a board's `workdir`/`extraFolders` refuse `DATA_DIR` and anything inside it (symlinks and `..` resolved), and on writes (delete, move, copy) also folders that contain it: 403 `{ error: "This folder is restricted to administrators" }`. Listings leave those folders out.

`/events` and `/terminal/stream` close within one heartbeat when the user's session is revoked, or the user is deactivated, deleted or changes role; the client reconnects with its current token.

## Users

Account management, **admin only**. Usernames are trimmed and lowercased, 2–32 characters of `a-z`, `0-9`, `.`, `_`, `-`, starting with a letter or digit; emails are optional (`null`), trimmed and lowercased, at most 254 characters; passwords 8–1024 characters. Username and email must be unique across accounts (409 `Username already taken` / `Email already in use`). Invalid fields answer 400; an unknown id 404 `User not found`. Every change is a `users` security event.

| Method | Path | Body | Response |
| --- | --- | --- | --- |
| GET | `/users` | – | `User[]`, oldest first |
| POST | `/users` | `CreateUserRequest`: `{ username, email?, password, role? }` (`role` default `"user"`) | `User` (201) |
| GET | `/users/:id` | – | `User` |
| PATCH | `/users/:id` | `UpdateUserRequest`: `Partial<{ username, email, role, isActive }>` | `User`. A role change or deactivation signs the user out everywhere (sessions and chat logins). 400 when you demote or deactivate your own account; 409 `At least one active admin is required` when it would leave no active admin |
| DELETE | `/users/:id?reassignTo=<userId>` | – | `DeleteUserResult`: `{ ok: true, boards, credentials, reassignedTo }`. With `reassignTo` (an active user other than `id`), the user's projects (with everything under them) and credentials move to that user (`board.updated` per project); without it each project is deleted like `DELETE /boards/:id` and their credentials are deleted (MCP entries using them are rewritten). `boards`/`credentials` count what moved or was deleted. 400 deleting yourself, `reassignTo` = `id`, or an unknown or inactive `reassignTo`; 409 deleting the last active admin |
| PATCH | `/users/:id/password` | `{ password }` | `{ ok: true }`; signs the user out everywhere. For your own account it answers a fresh `TokenResponse` instead, so you stay signed in |

Orchestration settings (**Settings → Orchestration**, all off by default; see docs/ADVANCED.md "Orchestration guardrails"): switches `runTimeLimit`, `stallWatchdog`, `runBudget`, `wrapUpNudge`, `loopDetection`, `gitCheckpoints`, `subagentLimits`, `contextCompaction`, `telemetryExport`, `loadGuard` must be booleans; `runTimeLimitMinutes` (integer 5–1440, default 120), `stallTimeoutMinutes` (integer 2–240, default 20), `runBudgetUsd` (number 0–10000, default 5; 0 = no dollar cap), `runBudgetTokens` (integer 0–1000000000, default 0 = no token cap), `wrapUpPercent` (integer 50–95, default 80), `subagentMaxConcurrency` (integer 1–32, default 8), `subagentMaxDepth` (integer 1–3, default 1 = subagents cannot delegate further), `subagentTimeoutMinutes` (integer 0–480, default 30; 0 = no limit), `contextCompactPercent` (integer 20–95, default 50) and `loadGuardPercent` (integer 10–1000, default 150) are validated against `ORCHESTRATION_LIMITS` (else 400 `<field> must be … between <min> and <max>`); `telemetryEndpoint` is `""` or an http(s) URL of at most 2048 characters. Out-of-range stored values are clamped on read.

`wrapUpNudge` needs `runTimeLimit` or `runBudget`: once a run has used `wrapUpPercent` % of whichever is further along (time, USD or tokens; below 100 %), the agent is steered once to stop starting new work, finish or pause the current step, verify and write its summary with its Report, and the run log gets `Wrap-up nudge: <P>% of the run time limit|run budget used (<detail>); asked the agent to finish up`. `subagentLimits` and `contextCompaction` apply to runs started after saving, through the run's omp `--config` overlay: `task.maxConcurrency` (the run's fair share of this machine: 2 subagents per core and one per 192 MB of free memory beyond the 10% reserve, divided by the card agents running here, capped at `subagentMaxConcurrency`, at least 1; runs on cluster nodes get `subagentMaxConcurrency`), `task.maxRecursionDepth` (`subagentMaxDepth`), `task.maxRuntimeMs` (`subagentTimeoutMinutes`, left out at 0) and `compaction.thresholdPercent` (`contextCompactPercent`). The run log shows `Subagents: up to N at once, depth D, M min each` and `Context compaction at P %`.

AI provider values (`/settings/ai-providers`) live in the settings table under `ai_providers`, each sealed with the credentials encryption key (AES-256-GCM, `CREDENTIALS_KEY` or `DATA_DIR/credentials.key`, see [Credentials](#credentials)); plaintext is never stored or logged and secret values are only returned masked. A saved value overrides the same environment variable inherited from the server's environment for every omp child process, applied at boot and on every save, so new keys work for the next agent without a restart. A value that can no longer be decrypted (the key changed) is reported as `broken` and the provider as `error` until it is entered again.

OAuth sign-ins (`/settings/ai-providers/oauth`) keep nothing in OMP-UI: `omp login` stores and refreshes the tokens in omp's own credential store (`~/.omp`, mounted read-write in Docker), which every omp child reads, so a sign-in applies to the next agent run. It shows up as the provider's `ompSignIn` (reported by `omp usage`) and its models: a catalog provider's `modelProviders` include the omp providers its sign-ins add (`openai-codex` for OpenAI; `google-gemini-cli` and `google-antigravity` for Google). Signing out is omp's `/logout`.

Scheduled data cleanup runs the OMP-UI-data cleanups of [`/stats/maintenance`](#stats) (`orphan-card-files`, `orphan-board-files`, `orphan-workspaces`, `run-configs`, `drafts`, `diff-cache`, `rotated-logs`, `database`; Docker prunes stay manual) on the server: about a minute after start and then hourly it checks whether one period (7 days weekly, 30 days monthly) has passed since the later of the last run (manual or scheduled) and the moment the schedule was chosen, so enabling a schedule never cleans right away. The last outcome is kept in the settings table under `cleanup_state`.

### Data transfer

**Settings → Data transfer** (admin only) moves a server to another machine. An export is a `.tar.gz` holding `manifest.json` (`{ format: "omp-ui-data", version: 1, appVersion, createdAt, driver, counts, credentialsKey: "file"|"env"|"none" }`), `db/<table>.jsonl` for every table (`settings`, `users` with password hashes, `boards`, `tasks`, `comments`, `runs`, `run_events`, `schedulers`, `scheduler_runs`) as driver-independent domain records (the same shapes the API returns; an export from one database driver imports into another), `files/` (`DATA_DIR/files`) and `credentials.key` (left out when `CREDENTIALS_KEY` sets the key). Project folders and omp's `~/.omp` are not included.

| Method | Path | Response |
| --- | --- | --- |
| GET | `/data-transfer` | `DataTransferStatus`: `{ driver, users, projects, cards, schedulers, filesBytes, credentialsKey: "env"\|"file", activeAgents, importing, backups: { name, size, createdAt }[] }` |
| GET | `/data-transfer/export` | The export as `application/gzip` (`omp-ui-data-<yyyymmdd-hhmmss>.tar.gz`), built before the response starts. Logged as a security event |
| POST | `/data-transfer/import?confirm=replace` | Raw `.tar.gz` body → `DataImportResult` `{ source: { appVersion, createdAt, driver }, counts, skipped, files, credentialsKey: "restored"\|"ignored"\|"set-env"\|"none", interrupted, backup, signedOut }`. Replaces **all** data: saves the current data to `DATA_DIR/backups/before-import-<stamp>.tar.gz` (newest 3 kept), replaces every table (one transaction on SQLite and PostgreSQL; MongoDB restores the backup when it fails midway), then `DATA_DIR/files` and `credentials.key`, and reloads the token secret, AI provider keys, MCP env and chat bots without a restart. Cards whose agent was running in the source fail with a note (Resume continues them), queued ones go idle, running runs end `aborted`; rows whose project, card, run or scheduler is missing are left out (`skipped`). `signedOut`: the caller's token no longer works (the import replaced the accounts or the token secret). 400 without `confirm=replace`, for anything but a valid export (wrong format, newer `version`, row counts not matching the manifest, links or special files in it, no active admin account) — nothing changes then; 409 while agents run or queue, or during another import |
| GET | `/data-transfer/backups/{name}` | Download a pre-import backup (an export; importing it restores that state). 404 for unknown names |

## Stats

| Method | Path | Response |
| --- | --- | --- |
| GET | `/stats/system` | `SystemStats`: host (hostname, OS, uptime, Node), CPU (model, cores, load average, usage % sampled over ~200 ms), memory, disk of the `DATA_DIR` filesystem (`null` if unavailable), server process (pid, uptime, RSS, heap), app counts (boards, tasks per status, agents running/queued), and `resourceGuard` (`ResourcePressure | null`, same shape as `concurrency.pressure` in `/queue`: `{ memoryPercent, cpuPercent, cpuWindowSec, memoryHoldPct, memoryResumePct, cpuHoldPct, cpuResumePct, cpuSustainSec, holding, heldSince, restartAfterMin, restartPending, sampledAt }`; `null` when the guard does not run). Bytes are bytes, durations seconds |
| GET | `/stats/ai?refresh=1` | NDJSON stream of `AiStatsEvent`s, one per line, each sent as soon as its source answers (the three run side by side): `{ type: "providers", activeProviders }` at once, then `{ type: "quota", at, quota }` (`omp usage --json`), `{ type: "balances", at, balances }` and `{ type: "usage", at, usage }` (`omp stats --json`) in whatever order they finish; `at` is when that part was read. A failure of the whole request ends the stream with `{ type: "error", message }`. Each part is cached 60 s server-side; `refresh=1` bypasses the cache |
| GET | `/stats/maintenance` | `MaintenanceReport` (~1 s): top CPU/memory processes plus every agent-related one, each tagged (`server`, `card-agent`, `helper`, `orphan-agent` for untracked omp agents of this `DATA_DIR` whose parent died, `agent-spawned`, `omp`, `user`, `system`) with `killable`; memory (available, swap, server heap, idle helper agents); storage cleanup items with estimated bytes and `risk` (`safe`/`review`), other large folders (read-only) and recommendations |
| POST | `/stats/maintenance` | `{ kind: "cleanup", ids }` (ids from `CLEANUP_IDS`: leftovers of deleted cards/projects, old run configs, drafts and change summaries, rotated logs, SQLite compaction, Docker prunes) · `{ kind: "kill", pids }` (SIGTERM, SIGKILL after 3 s, with killable children; never the server or its ancestors, never a running card's agent) · `{ kind: "release-memory" }` (close idle helper agents, full GC) · `{ kind: "stop-card", taskId }` → `MaintenanceResult { results: { id, ok, message, freedBytes }[], freedBytes }` |

The `quota` and `usage` parts each carry `available: boolean` and a plain-language `error` (e.g. `"omp is not installed"`, `"omp usage took too long to respond"`); a failing `omp` command never fails the request. Each quota limit has `usedFraction` (0–1), `windowLabel` (e.g. `"5 Hour"`) and `resetsAt` (ISO). `usage` has `totals` (requests, failures, tokens, cache read/write, `cacheRate`, `cacheSavings`, `avgTokensPerSecond`, `avgTtftMs`, `costUsd`), `byModel`, `byAgent` (per omp agent kind) and `series` (hourly requests, tokens and cost). Timestamps are ISO strings.

The `balances` part carries prepaid balances the server reads directly from provider APIs because `omp usage` cannot read them (currently DeepSeek, via `GET /user/balance` with `DEEPSEEK_API_KEY`): one `AiProviderBalance` per provider with `provider`, `currency` (ISO code, e.g. `"CNY"`/`"USD"`), `total`, `granted`, `toppedUp` (amounts, `null` when unreported) and `available` (whether the balance is enough for API calls). A missing key or a failed request simply omits the entry — it never fails the request.

A run whose node stays offline longer than 30 s fails with `<reason>; rescheduled` and its card is queued again without using an automatic retry.

## Boards (projects)

A board is one project. `workdir` is the main folder (omp runs there); `extraFolders` are additional folders that belong to the same project (e.g. separate frontend/backend repos), passed to omp as `--add-dir`. `pushBranch` (default `"main"`; boards created before it existed read `"main"`) is the branch **Push to main** and the header quick push land on in every project repo; it is created on `origin` if missing. **Create PR** and **Push to current branch** ignore it: they target each repo's default branch and current branch respectively. `defaultBranches` (default `{}`) names that default branch per repo, keyed by folder (`workdir` or an `extraFolders` entry, absolute): it is the branch **Create PR** targets. A repo with no entry uses its own `origin/HEAD`, then a local or remote `main`/`master`, then its checked-out branch, then `main`.

- `POST /boards/:id/tasks` with `{ text, position? }` (`text`: 1–2,000,000 characters) → `Task` (201) in `in_progress` with its agent started right away (whatever the board's `autoRun`); no agent rewrites the text.
- A single line of up to 100 characters is the title as typed, with an empty description. Otherwise the title is the first line (Markdown list and heading markers stripped; its first sentence when over 80 characters; clipped to 80) and the description is the text verbatim.
- Text over 20,000 characters is also saved word for word as the card file `brief.md`; the description is clipped and gets a line pointing the agent to it.

### Code changes

`GET /tasks/:id/diff` → `TaskDiff`: `{ taskId, repos, stats: { files, additions, deletions }, truncated, hash, generatedAt }`. One `RepoDiff` per project folder: `{ folder, name, isRepo, branch, baseRef, commitsAhead, files, truncated, command, error }`. `baseRef` is the ref committed changes are compared against (e.g. `origin/main`; `null` = uncommitted changes only), `commitsAhead` the commits on HEAD not on it, `command` a shell command that shows the full diff, `error` a plain-language git failure (`null` when fine). Each `DiffFile` is `{ path, oldPath, status: "A"|"M"|"D"|"R", additions, deletions, binary, untracked, patch, truncated }`; `patch` holds the unified diff hunks without the file header. Caps: 400 KB of patch text in total and 160 KB per file; untracked files over 256 KB and binary files are listed without content (`patch: null`, `truncated` or `binary` set). `hash` is a content hash of the changes.

`GET /tasks/:id/diff/summary` → `DiffSummary`: `{ text, source: "model"|"fallback", pending, error, hash }`. A cached summary (by `hash`, `DATA_DIR/runtime/diff-summaries/<hash>.json`) is answered as `source: "model"`; otherwise `text` is the deterministic file-count line (`source: "fallback"`, `pending: false`) and no agent runs, so opening the Review tab spends no tokens. `POST` the same path to have a helper agent write the summary (the **Summarize** / **Regenerate** button): it waits up to 15 s for it and answers the fallback with `pending: true` until it is done (or, when the agent fails, with the reason in `error`); `GET` again to read it.

### Code review

`Task.review` is the card's latest review decision, `TaskReview | null` (`null` until reviewed): `{ decision: "approved"|"changes_requested", hash, note, at }`. `hash` is the `TaskDiff.hash` the reviewer saw (`null` when unknown); runs never clear the review, so a current diff `hash` that differs from it means the review is stale. `note` is the reviewer's note (`null` when none); `at` the ISO time of the decision.

`POST /tasks/:id/review` with `{ decision, note?, hash? }` (`decision`: `"approve"` or `"request_changes"`, 400 otherwise; `note`: trimmed, at most 10,000 characters; `hash`: at most 128 characters, empty/absent = `null`):

- `approve`: 409 `The agent is still working; stop it or wait before approving` while the card's agent is queued or running. Stores `{ decision: "approved", hash, note, at }` (a blank or absent `note` is `null`) and moves the card to **Done** unless it is already there (the same agent rules as a PATCH `status` change). Answers `{ task, comment: null }`.
- `request_changes`: `note` is required (400 when absent or blank). Stores `{ decision: "changes_requested", hash, note, at }`, then posts a `user` comment `**Changes requested**\n\n<note>` exactly like `POST /tasks/:id/comments` (`comment.added` is published and the feedback steers the live run, or reopens and resumes the agent). Answers `{ task, comment }` (200; `task` re-read after the agent hook).

Either way `task.updated` is published with the final card.

### Trajectories

`GET /tasks/:id/trajectory` and `GET /boards/:id/trajectories` export card agent sessions in the ShareGPT JSONL format Hermes writes for debugging and training datasets, as `application/x-ndjson` downloads. Same access as the card (its owner or an admin).

- Each line: `{ conversations: [{ from: "system"|"human"|"gpt"|"tool", value }], timestamp, model, completed, taskId, runId, metrics? }`. A `gpt` turn holds the agent's text followed by each tool call as `<tool_call>\n{"name","arguments"}\n</tool_call>`; each result is a `tool` turn `<tool_response>\n{"name","content","is_error"}\n</tool_response>`. Thinking is dropped, images read `[image]`. `model` is `provider/model` when the session names one, else `null`; `completed` is whether the run succeeded (whole session: the agent is idle and its last run succeeded); `timestamp` is the run's end, else the export time; `runId` is `null` for the whole session.
- Single card: the whole omp session, or with `runId` only that run's time window (404 `Run not found` when it is not the card's run). 404 `No agent session for this card`; 413 for a session over 64 MB.
- Board: every card, or only those in `status` (400 for anything but `todo`, `in_progress`, `done`); cards without a readable session are left out. Sessions are read one at a time as the client takes each line; sessions over 64 MB are skipped, and cards beyond 256 MB of session input in total are left out.
- `compress=1` (or `true`) compresses each trajectory to `maxTokens` (integer 1,000–1,000,000, else 400; default 15,250), counting 4 characters per token, and adds `metrics` = `{ originalTokens, compressedTokens, tokensSaved, compressionRatio, turnsRemoved, toolResultsPruned }`. Under the target nothing changes. Over it, tool outputs over 2,000 characters outside the last 4 turns are cut to their first and last 200 characters (`… [N chars pruned] …`); if still over, middle turns are replaced by one `human` turn `[CONTEXT SUMMARY]: N turns compressed (tools used: …; E errors)`, keeping the leading turn group and the last 4 turns and never splitting a tool call from its responses.
- Secrets: known secret values (MCP credentials, AI provider keys, git host and npm tokens, OMP-UI's own secrets; 8+ characters, also as JSON-escaped) and common token shapes (`sk-…`, `ghp_…`, `github_pat_…`, `xoxa-`/`xoxb-`/`xoxp-…`, `AKIA…`) are replaced with `[REDACTED]`, before compression.
- At most 2 exports run at once across both routes; more answer 429.

## Agent queue

| Method | Path | Body | Response |
| --- | --- | --- | --- |
| GET | `/queue` | – | `QueueSnapshot`: `limit` (the effective limit, `concurrency.limit`), `concurrency` (see below), `running` and `queued` (start order) `QueueEntry`s, each with `createdByTaskId` (the card whose agent created it, or `null`) |
| POST | `/queue` | `{ taskId, position }` | `QueueSnapshot` after moving a queued card (`position` 0 starts next); 409 if the card is not queued |

Queued cards start in queue order as slots free up.

`concurrency` = `{ mode: "auto"|"manual", limit, boundBy: "cpu"|"memory"|"max"|"resources"|null, cpus, freeMemoryBytes, totalMemoryBytes, reason, pressure, agentMemoryBytes?, committedMemoryBytes? }`. With `maxConcurrentAgents: "auto"` (the default; `MAX_AGENTS=auto`), `limit` = min(logical cores, running agents + (free memory − 10% of RAM (at most 2 GB) − `committedMemoryBytes`) ÷ `agentMemoryBytes`, 32), re-checked every 30 s; `boundBy` names the bound that applied. `agentMemoryBytes` (auto mode) is learned: the 75th percentile of the peak memory of the last 20 runs that lived at least 2 min (at boot, seeded from cards whose stored `resources` show at least 30 CPU-seconds), clamped to 256 MB–4 GB, and 600 MB until 3 runs are known. `committedMemoryBytes` (auto mode) is memory still promised to running agents: Σ max(0, `agentMemoryBytes` − its current memory), an agent not sampled yet counting in full for its first 90 s. With a number, `mode` is `manual` and `boundBy` is `null`. `reason` is one line for the UI, e.g. `"Auto: 12 parallel (16 cores, 28 GB free, ~0.8 GB per agent)"`. `pressure` (`ResourcePressure | null`; `null` where the guard does not run) is the resource guard's latest sample, also while it holds nothing; `boundBy` is `"resources"` (and `limit` the agents running) while it holds queued cards: `{ memoryPercent, cpuPercent, cpuWindowSec, memoryHoldPct, memoryResumePct, cpuHoldPct, cpuResumePct, cpuSustainSec, holding, heldSince, restartAfterMin, restartPending, sampledAt }` where `holding` is an array of held resources (`"memory"`, `"cpu"`), `heldSince` is an ISO string or `null`, `cpuPercent` is `number | null`, `restartPending` is true when memory held for at least `restartAfterMin` (graceful restart happens once no agent runs and cards are queued), and `restartAfterMin` is `0` when the restart is off or the server is not supervised.

### Git buttons (Push to main / Push to current branch / Create PR)

All act on every project folder (`workdir` + `extraFolders`), or only on `folders` (each must be one of the project folders), one folder at a time. A failure in one folder doesn't stop the others; each folder gets a `GitRepoActionResult`.

- 409 while the task's agent is queued or running (“Wait for the agent to finish first.”). 400 if none of the folders is a git repository.
- Folders that are not git repositories, or have nothing to commit or push, are returned with `skipped: true`.
- **Push to main**: fetches `origin/<pushBranch>`, commits uncommitted changes if any (`git add -A`, message = `message` or the task title), merges `origin/<pushBranch>` into HEAD (`git merge --no-edit`; the pull that keeps a remote which moved on from rejecting the push), then `git push origin HEAD:refs/heads/<pushBranch>` with the board's `pushBranch` (default `main`), creating that branch on `origin` if it doesn't exist; the result's `branch` and the comment name it. `url` links to the pushed commit on GitHub/GitLab, otherwise to the repository page. A conflicting merge is aborted (the folder is left as it was) and that folder's `error` explains it and suggests Create PR; a protected branch likewise. When at least one folder was pushed and none failed, the task's `pushedAt` is set to now (the UI strikes through the card's title).
- **Push to current branch**: same as Push to main, but each folder targets the branch it is currently on (`git push origin HEAD:refs/heads/<that branch>`), created on `origin` if missing (before the push, that same branch's `origin` counterpart is merged in); a folder on a detached HEAD has no current branch and reports an `error`. `pushedAt` is set only when every folder landed on the board's `pushBranch`.
- **Create PR**: builds the PR branch `omp/<task-slug>-<random>` without touching the folder's checked-out branch, index or working tree: it fetches the repo's default branch (the project's `Board.defaultBranches` entry for that folder, else `origin/HEAD`, falling back to `main`/`master`, then `main`; the board's `pushBranch` is not used; it must exist on `origin` or locally, else the folder's result carries an error), replays only the card's own changes on top of it as one commit (message = PR title), pushes that commit as `refs/heads/<branch>`, then opens a PR with `gh` (GitHub) or an MR with `glab` (GitLab) against that default branch. The card's own changes are the start→end differences of its runs in that folder: each run stores a tree snapshot of every git project folder when it starts and when it ends as commits under `refs/omp-ui/task-runs/<taskId>/<runKey>/{start,end}` (a run without a recorded end lasts until the next run starts, or until now); they are removed with the card. Changes made by the user or other cards outside the card's runs stay out. A folder where the card has no recorded run reports an error (“no record of what this card changed here”); one whose changes don't apply on the default branch (they depend on commits that aren't there) or leave the default branch's tree unchanged is reported as an error or skipped respectively. PR title defaults to the task title; body defaults to a compact description (`lib/pr-body.ts`): the latest agent summary's prose (without its `## Report` section and OMP-UI-relative images/links, clipped to 1500 chars), its `Outcome`/`Tests`/`Changes` lines as bullets, the task description collapsed in `<details>` (clipped to 2000 chars; shown plainly when there is no summary), then “Created from OMP-UI”. Without the CLI (or if it fails, e.g. not signed in), the branch is still pushed and `url` is the provider's “new pull request” page, so the user can open it with one tap.
- If no identity is configured for git on the server, commits are made as `OMP-UI <omp-ui@localhost>`.
- Afterwards one resolved `agent` comment summarising the result in plain language (with links) is posted on the task and returned as `comment`; `comment.added` and `task.updated` are published.

### Agent rules

- Move a card to **In progress** (PATCH `status`) → omp agent starts in the board `workdir` (when the board has `autoRun`; otherwise call `POST /tasks/:id/run`).
- The web UI creates new cards on `autoRun` boards with `status: "in_progress"`, so they start right away (unless the user opts out). API clients choose `status` themselves; the default is still `todo`.
- Agent finishes successfully → its final message is posted as an `agent` comment, every open feedback comment included in the run is **auto-resolved**, and the card moves to **Done**. If that message asks the user something, the question is stored on `task.question` (cleared when the next run starts or via PATCH `question: null`); the web UI shows it on the card and lets the user answer with one click.
- Agent fails → card stays in **In progress** with `agentState: "error"` and an agent comment explaining the error. With `autoRetry` on, the run is retried automatically in the same omp session. Quota errors (`agentError` matching quota, usage limit, rate limit, 429, too many requests, resource exhausted, insufficient_quota, credit balance or out of credits) wait 5, 10, 15, 30 min, then 60 min for every later retry; other errors wait 15 s, 30 s, 1 min, 2 min, 4 min … (at most 10 min apart). With `persistentRetry` on (default) a failed run is always retried, whatever `maxAutoRetries` is, until the card is Done or stopped; with it off, retries stop once `task.autoRetries` (retries used) reaches `maxAutoRetries`. `task.autoRetries` counts retries either way; `task.retryAt` is when the next one starts (null when none is scheduled). A success, `POST /tasks/:id/run` or a feedback comment resets `autoRetries` to 0; Stop or moving the card out of In progress cancels a pending retry. The UI shows such a card as **Waiting for quota** when its `agentError` is a quota error, else **Retrying**.
- Server restart (boot recovery, on the first API call — the supervisor's health probe makes that immediate): runs left `running` are marked `aborted`; queued cards are queued again; with `autoRetry` on, cards that were running and failed In progress cards resume (each using one retry, bounded by `maxAutoRetries` even with `persistentRetry` on, so a card whose run keeps taking the server down stops once its budget is used up) and pending retries keep their `retryAt`. With `autoRetry` off, cards that were running end with `agentError: "Interrupted by server restart"`.
- Agent updates its todo list (omp `todo` tool) → `task.todos` (`TodoPhase[]`: `{ name, tasks: { content, status: "pending" | "in_progress" | "completed" | "abandoned", startedAt?, completedAt? }[] }`) is replaced with the latest list and `task.updated` is published. The server stamps `startedAt` (first seen in progress during the current run; an item completed without being seen in progress gets the run's previous list update) and `completedAt` (first seen completed), carried across updates by item content; while the agent runs, cards show the remaining-time estimate these give (completed items' working time per item × items left); the list stays after the run ends and is `[]` until the agent keeps one. Read-only: PATCH ignores it. The todo phases are whatever omp names them; OMP-UI imposes no workflow on them.
- Comment on a **Done** card (or an idle In-progress card) → card reopens to **In progress** and the agent resumes the same omp session with the feedback.
- Comment while the agent is **running** → feedback is steered into the live session right away as an RPC `prompt` with `streamingBehavior: "steer"`, exactly like typing into omp mid-run: the user's text goes in word for word (so magic keywords such as `orchestrate` apply; a message from another card's agent is introduced with its sender and its keywords are neutralized). The live, not persisted SSE event `comment.steer` `{ commentId, taskId, boardId, state }` reports what became of it: `sent` (omp took it; it reaches the agent at its next step), `delivered` (it left omp's steering queue, or the turn it joined ended), `deferred` (the run was wrapping up or omp declined it; the next run picks it up). The card's Activity chat shows it under the comment.
- Move to **To do**/**Done** manually while running → agent is stopped.
- The web UI never sets an arbitrary status: cards move by themselves as their agent works, and the only status-affecting controls are its quick actions — **Start**/**Resume**/**Retry** = `POST /tasks/:id/run`, **Stop** = `POST /tasks/:id/stop`, **Revert to To do** = `PATCH /tasks/:id` with `{ status: "todo" }`. Done cards not pushed yet also get **Push to main** = `POST /tasks/:id/git/push` (no status change). Dragging in the UI only reorders within a column (PATCH `position`). API clients can still PATCH any `status`.
- **Task artifact cleanup**: a convention of the repo's `AGENTS.md`, not a prompt: OMP-UI adds nothing to the agent's prompt. The server deletes no files itself; Docker resources marked for the card (label `omp-ui.task=<taskId>` or compose project `task-<taskId>`; containers inherit the labels of a marked image they start from) are removed by `removeTaskDockerResources` (`lib/docker.ts`) when a run moves the card to Done and, in the background (`queueTaskDockerCleanup`), when the card or its project is deleted. Policy: [TASK-CLEANUP.md](TASK-CLEANUP.md).

### Workspaces, files, browser and collaboration

- **Shared project folders**: every card's agent runs in the project's folders (`workdir` + `extraFolders`) on the branch checked out there. Before the agent starts and after each run, a tree snapshot of every git folder is recorded (`lib/server/task-changes.ts`) to tell the card's changes from the user's and other cards'; the agent is told to stay on the checked-out branch.
- **Files**: every run gets the card's folder (`DATA_DIR/files/tasks/<taskId>`) and the board's (`DATA_DIR/files/boards/<boardId>`) as `--add-dir`. `files.updated` is published on upload/delete and when a run ends.
- **Browser control** (`AppSettings.browser`: `off` · `headless` · `visible` · `relay`): written to a per-run omp config overlay (`--config`); screenshots go to the card's `screenshots/` folder.

## Terminal

One persistent, server-wide shell session for the `/terminal` page, with tmux-like semantics: commands keep running when the browser leaves `/terminal` and even across an app restart; revisiting re-attaches and replays every block with its output. Types and limits are in [`lib/terminal-types.ts`](../lib/terminal-types.ts); the session manager is [`lib/server/terminal.ts`](../lib/server/terminal.ts).

Each command is its own `/bin/bash -c` process (`/bin/sh` without bash), detached in its own process group, run **as the server user** with the server's environment minus OMP-UI's secrets (`ADMIN_PASSWORD`, `AUTH_SECRET`, database URLs, `OMP_UI_*`), plus `TERM=xterm-256color`, `COLUMNS=120`, `PAGER=cat` and `GIT_PAGER=cat`. stdin is empty, so interactive programs see end of input. stdout and stderr go to one log file, interleaved as written.

| Method | Path | Body | Response |
| --- | --- | --- | --- |
| GET | `/terminal/stream` | – | `200 text/event-stream` (below) |
| POST | `/terminal/execute` | `TerminalExecuteRequest`: `{ command, cwd? }`. `command`: non-empty, at most 16384 chars; `cwd`: an absolute path to an existing directory (default: the session cwd) | `201 TerminalBlock` (`status: "running"`). 400 for an empty or too long command, or `"Directory not found: <cwd>"` for a relative or missing `cwd`; 429 when 8 commands are already running |
| POST | `/terminal/cancel` | `{ id }` | `{ ok: true }`. Kills the block's process group: SIGTERM, then SIGKILL 2 s later. 404 for an unknown id; a finished block is a no-op |
| DELETE | `/terminal/session` | – | `{ ok: true }`. Removes finished blocks and their logs; running blocks stay. Every stream receives a fresh `snapshot` |

The stream's unnamed messages are `data: <TerminalStreamEvent JSON>\n\n`:

- `snapshot` (first frame of every connection, and after a clear): `{ cwd, home, blocks, output, skipped }`. `blocks` oldest first; `output[id]` is each block's output so far, at most its last 512 KiB (`skipped[id]` = bytes dropped from the start). Live events continue exactly where the snapshot ends, so a client replaces its state with every snapshot and never refetches.
- `block` (`{ block, cwd }`): a block was added or changed (started, cancelled, timed out, truncated, finished); upsert by `id`. `cwd` is the session cwd.
- `output` (`{ id, data }`): new UTF-8 output of a running block, in order.
- A named `ping` event (empty data) every 15 s, so clients can detect a silent connection and reconnect.

`TerminalBlock`: `{ id, command, cwd, startedAt, pid, status, exitCode, signal, durationMs, timedOut, truncated, cancelled, outputBytes, endCwd, error? }`. `exitCode` is `null` when the command was killed by a signal (`signal`, e.g. `"SIGTERM"`), never started (`error` says why) or vanished without reporting (`error: "lost"`, e.g. killed with SIGKILL while the server was down).

- **`cd` persists**: a block's `endCwd` is the directory it ended in (also after `exit N`); the most recently finished block's `endCwd` becomes the session cwd, where the next command without `cwd` starts.
- **Persistence**: everything lives in `DATA_DIR/terminal/` (mode 0700): `session.json` (session cwd and blocks, replaced atomically on every change) and per block `<id>.log` (output), `<id>.cwd` and `<id>.exit` (written by the shell when it ends). A restarted server reloads the session, resumes streaming the commands that are still running and finalizes those that ended meanwhile. Stopping the server does not stop the commands.
- **Limits**: a command is killed after 6 hours (`timedOut: true`); a log is served up to 8 MiB, past that the command is killed and the rest is not served (`truncated: true`). The 100 most recent finished blocks are kept, older ones are deleted with their files.
- **Background jobs** (`cmd &`) keep running after the command ends, but their later output is not served once the block is done.

## Credentials

Keys and tokens for MCP servers and connector services, saved through the MCP connect dialog (there is no separate page). Types are in [`lib/credential-types.ts`](../lib/credential-types.ts); provider templates (fields, validation patterns, MCP launch config, health check) in [`lib/credential-providers.ts`](../lib/credential-providers.ts). Records live in the database settings (`credentials`, plus read/dismissed notification ids in `credential_notifications`). Secret fields are encrypted with AES-256-GCM under `CREDENTIALS_KEY` (any non-empty string, hashed with SHA-256) or else a generated `DATA_DIR/credentials.key`, and are only ever returned masked (`abcd••••wxyz`, or `••••••••` under 12 characters). With a different key, stored secrets cannot be decrypted: those credentials turn `failing` ("Cannot decrypt: the encryption key changed") until their secrets are entered again.

Credentials belong to the user who created them (`CredentialSummary.userId`; credentials from before the multi-user upgrade belong to the first admin). Regular users list, read, change, test and get notifications for their own only; another user's id answers 404 `Credential not found`. Admins see every credential. Background health checks and the MCP environment of every agent use all credentials regardless of owner.

Errors: invalid fields answer `400 { error, fields: CredentialValidationErrors }` (`error` is the first message; `fields` maps field keys, `name` and `expiresAt` to messages); an unknown provider or notification action `400 { error }`; an unknown id `404 { error }`; a conflicting concurrent edit `409 { error }`.

| GET | `/credentials` | – | `CredentialsResponse`: `{ credentials: CredentialSummary[], checkIntervalMs, keySource: "env"\|"file" }`. `keySource` says whether the encryption key comes from `CREDENTIALS_KEY` or `DATA_DIR/credentials.key` |
| POST | `/credentials` | `CredentialInput` (`{ providerId, name, fields, expiresAt?, autoCheck? }`; `autoCheck` defaults to `true`) plus `test?: boolean` | `201 CredentialSummary`. Fields are validated against the provider template (required fields, `pattern`, http(s) URLs, `select` options, no unknown keys; `name` ≤ 80 chars; `expiresAt` a date or `null`). With `test: true` the health check runs first, so the credential starts `healthy` or `failing` instead of `untested` |
| PATCH | `/credentials/:id` | `CredentialUpdate` (`{ name?, fields?, clear?, expiresAt?, autoCheck? }`) plus `test?: boolean` | `CredentialSummary`. `providerId` cannot change. | POST | `/credentials/test` | `CredentialInput` plus `id?` | `CredentialTestResult`: tests unsaved form values without storing anything; with `id`, secret fields left empty use that credential's stored values |
| POST | `/credentials/check-all` | – | `CredentialsResponse` after health-checking every credential the caller can see (also those with `autoCheck` off) |
| GET | `/credentials/notifications` | – | `CredentialNotificationsResponse`: `{ notifications: CredentialNotification[], unread }`, not dismissed, newest first |
| POST | `/credentials/notifications` | `{ action: "read"\|"dismiss"\|"read-all"\|"dismiss-all", ids?: string[] }` (`ids` for `read`/`dismiss`) | `CredentialNotificationsResponse` after the change |

- `CredentialSummary` = `{ id, providerId, name, fields, secretsSet, expiresAt, autoCheck, health: "healthy"\|"failing"\|"untested", lastCheckedAt, lastOkAt, lastLatencyMs, lastMessage, failingSince, consecutiveFailures, userId, createdAt, updatedAt }`. `fields` holds non-secret values verbatim and secret ones masked; `secretsSet` lists the secret fields that hold a value; `userId` is the owner's id.
- `CredentialTestResult` = `{ ok, message, latencyMs, checkedAt }`. Each provider's check is one authenticated request (e.g. `GET {host}/user` for GitHub, an MCP `initialize` call for a custom MCP server) with a 10 s timeout; `message` is short and never contains the secret ("Authenticated as octocat", "401 Unauthorized: Bad credentials", "Timed out after 10 s").
- Credentials with `autoCheck` are re-checked in the background every 10 minutes (`checkIntervalMs`, `CREDENTIAL_CHECK_INTERVAL_MS`), first about 30 s after the server starts.
- `CredentialNotification` = `{ id, credentialId, credentialName, providerId, kind: "failing"\|"expired"\|"expiring"\|"untested", severity: "error"\|"warning"\|"info", title, message, createdAt, read }`. Notifications are derived from the credentials on every read: `failing` and `expired` are errors, `expiring` (within 7 days of `expiresAt`) a warning, `untested` (never checked, created over an hour ago) info. `id` is `${credentialId}:${kind}:${since}`, so a new occurrence of a problem (failing again after recovering) is a new, unread notification even if the old one was dismissed.

## MCP servers

MCP servers OMP-UI connects to every agent it starts (the `/mcp` page). Types are in [`lib/mcp-types.ts`](../lib/mcp-types.ts), the curated catalog in [`lib/mcp-catalog.ts`](../lib/mcp-catalog.ts); logic in [`lib/server/mcp.ts`](../lib/server/mcp.ts). Each connected server is a catalog [credential provider](#credentials) with an MCP launch spec plus a saved credential of that provider, written as one entry under `mcpServers` in omp's user MCP config: `<omp agent dir>/mcp.json` (the agent dir `omp config path` reports, see [OMP config](#omp-config)). OMP-UI's own record of each server (name, provider, credential, enabled, last probe) lives in the database settings (`mcp_servers`). Every write keeps the file's other entries and top-level keys verbatim (servers added by hand, `/mcp add`, other tools), adds `$schema` when missing, and replaces the file atomically; an unparsable file is never overwritten. Entries OMP-UI did not write are listed under `external`, read-only.

Secrets never reach mcp.json: an entry references them as `${OMPUI_MCP_<SERVER>_<FIELD>}` placeholders (server name upper-cased with every other character as `_`, field key in UPPER_SNAKE_CASE: server `my-server`, field `token` → `${OMPUI_MCP_MY_SERVER_TOKEN}`), which omp expands from its environment when it loads the file; non-secret values (URLs, regions, …) are inlined. OMP-UI decrypts the values into the environment of every omp process it starts (card runs, chat, helpers, the in-app terminal), so its agents get the server's tools as `mcp__<server>_<tool>` (omp turns other characters of the server name into `_`: server `my-server` → `mcp__my_server_<tool>`). omp sessions started outside OMP-UI read the same file but do not get these variables, so the servers' secrets are missing there. Editing or deleting a credential (`PATCH`/`DELETE /credentials/:id`) re-syncs mcp.json and the agents' environment: a server whose credential is deleted stays in the file with `enabled: false`.

Errors: invalid fields of a new credential answer `400 { error, fields }` as for [`POST /credentials`](#credentials); an invalid body, server name or provider without an MCP launch spec `400 { error }`; an unknown server or `credentialId` `404 { error }`; a server name already used in mcp.json (by OMP-UI or not) `409 { error }`; mcp.json that cannot be read, parsed or written (omp not found, invalid JSON) `502 { error }`, leaving the file untouched and saving no new credential.

- `McpServerSummary` = `{ name, providerId, credentialId, credential: CredentialSummary\|null, enabled, status, statusMessage, transport: "stdio"\|"http", config: McpServerConfig, synced, probe: McpProbeResult\|null, createdAt, updatedAt }`. `config` is the entry exactly as written (secrets as placeholders, safe to show and copy): `{ type: "stdio", command, args, env? }` or `{ type: "http", url, headers? }`, plus `enabled: false` when switched off. `synced` says mcp.json currently holds exactly `config` under `name`; `credential` is `null` once the credential is deleted.

Catalog entries without a server are shown as "not configured" by the page.
- `McpProbeResult` = `{ ok, message, serverName, serverVersion, tools: { name, description? }[], latencyMs, checkedAt }`. The probe starts the server as omp would (stdio: the command with its environment; http: a JSON-RPC POST with its headers), sends `initialize` and `tools/list`, and gives up after 20 s for http and 90 s for stdio (first `npx`/`uvx` runs download the package). `message` (e.g. "Connected to github-mcp-server 0.9.1 · 51 tools") never contains a secret.
- `McpDirectoryEntry` = `{ path, name, owner, featured, url, updatedAt }`: `path` is the page on mcpservers.org (`/servers/github-mcp-server`, `/servers/<owner>/<repo>`), `url` the full link, `name` derived from the slug ("Github MCP Server"), `owner` the publisher of `/servers/<owner>/<repo>` pages (else `null`), `updatedAt` the sitemap's `lastmod` (or `null`). Featured servers come first in the site's order, then the newest. The page itself has the description and setup steps.

## Schedulers

Recurring cards (the `/schedulers` page). On every match of its cron expression, evaluated in its IANA time zone, a scheduler creates a regular card on its project from its `prompt`, through the same [free-text flow](#new-cards-from-text) as `POST /boards/:id/tasks` with `text`. The card starts its agent even when the project has `autoRun` off, and carries `Task.schedulerId` (the scheduler's id; `null` for cards a person or an agent created, and once the scheduler is deleted). Logic in [`lib/scheduler.ts`](../lib/scheduler.ts), cron parsing in [`lib/cron.ts`](../lib/cron.ts).

| Method | Path | Body | Response |
| --- | --- | --- | --- |
| GET | `/schedulers?boardId=<id>` | – | `Scheduler[]`, newest first; `boardId` (optional) limits them to one project, 404 if it doesn't exist |
| POST | `/schedulers` | `{ boardId, prompt, cron, timezone?, name?, enabled?, maxRuns?, model? }` | `Scheduler` (201). `name` (≤ 100 chars) defaults to the prompt's first non-empty line (cut to 100 chars), `timezone` to `"UTC"`, `enabled` to `true`, `maxRuns` to `null` (forever; else 1–100000), `model` to `null` (an omp selector such as `"anthropic/claude-sonnet-4-5"`: every card the scheduler creates runs on it, over the project's model; `null` = the project's model, else the usual selection). `nextRunAt` is computed right away. 400 for a bad cron expression, time zone or field; 404 for an unknown project |
| GET | `/schedulers/:id` | – | `Scheduler` |
| PATCH | `/schedulers/:id` | `Partial<{ boardId, name, prompt, cron, timezone, enabled, maxRuns, model }>` | `Scheduler`. `nextRunAt` is recomputed from now when `cron`, `timezone`, `enabled` or `maxRuns` change (`null` while disabled). 400 `"Run limit reached: raise or clear maxRuns to enable"` when the result would be enabled with `runCount ≥ maxRuns`; 404 for an unknown `boardId` |
| DELETE | `/schedulers/:id` | – | `{ ok: true }`. Deletes its run history; the cards it created stay, with `schedulerId` set to `null` |
| POST | `/schedulers/:id/run` | – | `SchedulerRunView` (201): fires it now, also while disabled (`trigger: "manual"`). Counts toward `maxRuns`; a failure to create the card is a run with `status: "failed"`, not an HTTP error |
| GET | `/schedulers/:id/runs` | – | `SchedulerRunView[]`, newest first (latest 200) |
| GET | `/schedulers/:id/logs` | – | `SchedulerLogEntry[]`, oldest first: for its latest 20 runs, one `scheduler` line per run plus the `status`, `text`, `tool` and `error` events of every agent run of the card it created (while the card exists). At most the newest 2000 entries |
| POST | `/schedulers/chat` | `SchedulerChatRequest` | NDJSON stream of `SchedulerChatEvent` (`application/x-ndjson`): one turn of **Create with Agent**. Saves nothing; 400 for a malformed body or when the user has no project. Closing the request cancels the assistant |

- `Scheduler` = `{ id, boardId, name, prompt, cron, timezone, enabled, maxRuns, runCount, lastRunAt, nextRunAt, lastStatus: "created"\|"failed"\|null, lastTaskId, lastError, model, createdAt, updatedAt }`. `runCount` counts every run (scheduled and manual, successful or not); `lastTaskId` is the card of the last successful run (kept when a later run fails); `lastError` is the last run's error, `null` when it succeeded. `nextRunAt` is `null` when disabled, when `maxRuns` is reached, or when the expression matches nothing in the next 5 years.
- `SchedulerRun` = `{ id, schedulerId, taskId, trigger: "scheduled"\|"manual", scheduledFor, status: "created"\|"failed", error, createdAt }`. `scheduledFor` is the cron slot the run was for (scheduled) or the click time (manual); `taskId` is `null` when it failed. A run stays in the history when its card is deleted.
- `SchedulerRunView` = `SchedulerRun` plus `task` (live snapshot of its card: `{ id, title, status, agentState, agentError, lastRunId }`, `null` once the card is deleted or when the run failed) and `runStatus` (status of the card's latest agent run, else `null`).
- `SchedulerChatRequest` = `{ messages: { role: "user"\|"assistant", text }[], timezone, boardId?, draft? }`: the whole conversation so far (the last message the user's, at most 20,000 characters; the newest 30 are used), the user's IANA time zone (used when they name none), the project to default to (else the first) and the draft currently shown (so follow-ups revise it). A scheduler assistant (an omp helper agent on the default model, with no built-in tools; only the signed-in user's projects and schedulers) answers through two host tools: `omp_ui_propose_scheduler` validates a complete scheduler like `POST /schedulers` (plus "the cron must match a future date") and returns the problem to the agent when it is invalid, `omp_ui_list_schedulers` lists the existing ones.
- `SchedulerChatEvent` = `{ type: "activity", text }` (progress lines) … then exactly one `{ type: "done", reply, draft }` or `{ type: "error", error }`. `draft` is the last `SchedulerDraft` proposed this turn, `null` when the assistant only answered (e.g. asked a question). `SchedulerDraft` = `{ boardId, name, prompt, cron, timezone, enabled, maxRuns, model }`, the exact `POST /schedulers` body to create it.
- `SchedulerLogEntry` = `{ at, kind: "scheduler"\|"status"\|"text"\|"tool"\|"error", text, schedulerRunId, taskId, runId }`. `runId` is the card's agent run (`null` on `scheduler` lines).
- **Cron syntax**: exactly 5 space-separated fields: minute `0-59`, hour `0-23`, day of month `1-31`, month `1-12` or `JAN`–`DEC`, day of week `0-7` (0 and 7 are Sunday) or `SUN`–`SAT`; names are case-insensitive. Each field takes `*`, `n`, ranges `a-b`, steps `*/n`, `a-b/n` and `a/n` (from `a` to the field's maximum), and comma lists of these. Macros: `@yearly` (= `@annually`), `@monthly`, `@weekly`, `@daily` (= `@midnight`), `@hourly`. `?`, `L`, `W`, `#` and `@reboot` are rejected (400). As in Vixie cron, when both day of month and day of week are restricted (neither starts with `*`), a day matches when **either** matches (`0 9 1 * MON` = the 1st of the month and every Monday).
- **Time zone**: the expression is evaluated in the scheduler's wall-clock time (`timezone`, e.g. `"Europe/Berlin"`), so `0 9 * * *` fires at 09:00 local time all year round. Across DST changes: a wall-clock time skipped by the spring-forward jump does not fire that day (it is not moved to another instant); a time repeated by the fall-back hour fires once, at its first occurrence. Each wall-clock minute fires at most once.
- **Due check**: the server checks every 30 s (first about 10 s after it starts) and fires each enabled scheduler whose `nextRunAt` has passed. Before creating the card it saves the next fire time after now, so a slot never fires twice, even across overlapping checks or a crash. Slots missed while the server was down fire **once** on catch-up (`scheduledFor` = the first missed slot), then the schedule continues from now.
- **Run limit**: after the run that makes `runCount` reach `maxRuns` (scheduled or manual), the scheduler disables itself (`enabled: false`, `nextRunAt: null`). Re-enabling it needs a higher `maxRuns` or `maxRuns: null`.
- **Failures**: a missing project ("Project not found") or an error while creating the card records a `failed` run with its `error` and sets `lastStatus`/`lastError`; the schedule continues.
- **Events**: every create, edit and run publishes `scheduler.updated` (`{ scheduler }`); deleting publishes `scheduler.deleted` (`{ schedulerId, boardId }`). The cards it creates publish the usual `task.updated` events.

## Live updates

`GET /events?boardId=<id>` – Server-Sent Events. Each message: `data: <ServerEvent JSON>\n\n`. Omit `boardId` to receive everything the caller can see (regular users: events of their own projects only); `queue.updated` is sent on every stream (for regular users, reduced to their own cards). A named `ping` event (`event: ping\ndata:\n\n`, not delivered to `onmessage`) is sent every 20 s so clients can detect a silent connection and reconnect. The stream closes within one heartbeat when the session is revoked or the user is deactivated, deleted or changes role.

Run events of kind `agent` hold a JSON `SubagentSnapshot` (one subagent of an orchestrated run); the latest per `id` is its state. They are written when a subagent appears, changes status or reports, and when the run ends (subagents still working are marked `aborted`). Progress in between is sent only live as `run.agent`.

`Task.resources` (`AgentResources | null`) is the memory and CPU of the card's latest agent run: its omp process plus every process it started, as `{ memoryBytes, peakMemoryBytes, cpuPercent, cpuSeconds, sampledAt }` (`cpuPercent` is percent of one core since the previous sample; `cpuSeconds` the CPU time since the run started). While a run is going it is sampled every 5 s and sent only live as `run.resources` (`{ runId, taskId, boardId, resources }`); the last sample is stored on the card when the run ends (with a `task.updated`), and the field is cleared when the next run starts. `null` when the card never ran or sampling is unsupported (Windows). Read-only: PATCH ignores it.

`Task.usage` (`TaskUsage | null`) is the estimated model spend of the card's omp session over all its runs: `{ costUsd, totalTokens, inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, requests, updatedAt }`. It is summed from the `usage` omp records on every model response in the session files (`lib/agent/session-usage.ts`): the card's session JSONL (assistant messages and `model_usage` side requests) plus every subagent's JSONL in the session's artifact directory, so context compaction and async subagents don't lose spend. `costUsd` is omp's estimate at the models' list prices; `totalTokens` is omp's `totalTokens` (input + output + cache read + cache write). While a run goes it is rescanned at most every 15 s (incrementally) and stored when it changed, then once more when the run ends, each time with a `task.updated`; a patch that only sets `usage` leaves `updatedAt` unchanged. When a run starts a new omp session, the earlier session's stored spend carries over. At boot, finished cards with a session but no stored usage are tallied once in the background. `null` until the card's session made a model request. Read-only: PATCH ignores it.
