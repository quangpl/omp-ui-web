REST API

Base path: /api/v1. JSON in/out. Errors: HTTP 4xx/5xx with { "error": "message" }. Designed for the web UI and future mobile clients: a client only needs the server URL and a username (or email) and password.

#Authentication

Method Path Body Response Auth
GET /auth/status – AuthStatus: { configured: boolean, authenticated: boolean, user: User | null }. configured: at least one account exists; user: the signed-in account none
POST /auth/setup { username?, email?, password } (username default "admin"; password min 8 chars) TokenResponse + cookie. Creates the first account, an admin. 400 for an invalid username, email or password none; only while no account exists (409 otherwise)
POST /auth/login { username?, password } TokenResponse + cookie. username is a username or an email (case-insensitive); omitted or empty → "admin" (password-only clients). 401 { error: "Invalid username or password" } (also for a deactivated account); 409 before setup none; rate limited (429 with retry-after)
POST /auth/logout – { ok: true }, clears cookie any
POST /auth/password { current, next } TokenResponse for this session. Changes the caller's password and signs out the caller's other sessions and chat logins; other accounts are untouched. 403 wrong current, 400 next under 8 chars required

TokenResponse = { token, expiresAt, user: User }. User = { id, username, email: string \| null, role: "admin" \| "user", isActive, createdAt, updatedAt }.

Authenticated requests send either the omp_ui_token httpOnly cookie (web) or Authorization: Bearer <token> (mobile/CLI). Tokens (format v2) are HMAC-SHA256 signed, valid 30 days and bound to one account: they stop working when that account's password changes (by itself, an admin or omp-ui passwd), or when it is deactivated, changes role or is deleted. Bumping the global epoch (settings key token_epoch) revokes every account's tokens at once. Tokens issued before the multi-user upgrade (v1) are rejected, so every client signs in once more.

Upgrades: the old admin password becomes the account admin, and every existing project, card and credential is assigned to the first admin at boot. The ADMIN_PASSWORD env var, when set, is applied at every boot to the admin account: created if missing, made an active admin, and signed out when the password differs from the stored one. omp-ui passwd writes ADMIN_PASSWORD to .env, so it resets the admin account only (at the next boot).

#Access control

Data is per user: a regular user (role: "user") sees and changes only their own projects and everything under them (cards, comments, runs and run events, schedulers, artifacts, card and project files, workspaces, git actions), their own credentials, and only those in live events (/events), the agent queue (/queue) and the dashboard. New projects and credentials belong to their creator. Admins see and change everyone's data. An id the caller cannot see answers 404 exactly like an unknown one.

Admin only (403 { error: "Admin only" } for regular users, recorded as a security event):

  • every method: /users/**, /terminal/**, /docker/**, /logs/** except POST /logs/access (the page-view beacon), /settings/cleanup, /settings/telemetry/test, /settings/ai-providers/oauth/**, /stats/maintenance, /mcp/sync, /mcp/:name/test, /chat/{telegram,discord}/{connect,disconnect}.
  • mutations only (GET stays open): POST /system/restart, PATCH /settings, PUT /omp-config, PATCH /settings/ai-providers, POST /settings/ai-providers/test, POST /mcp, PATCH/DELETE /mcp/:name.

For regular users GET /omp-config answers raw: "" and version: "" (the file may hold secrets).

Data directory: for regular users, /fs/**, /git/init, /git/repo, /git/clone, the project-files routes and a board's workdir/extraFolders refuse DATA_DIR and anything inside it (symlinks and .. resolved), and on writes (delete, move, copy) also folders that contain it: 403 { error: "This folder is restricted to administrators" }. Listings leave those folders out.

/events and /terminal/stream close within one heartbeat when the user's session is revoked, or the user is deactivated, deleted or changes role; the client reconnects with its current token.

#Users

Account management, admin only. Usernames are trimmed and lowercased, 2–32 characters of a-z, 0-9, ., _, -, starting with a letter or digit; emails are optional (null), trimmed and lowercased, at most 254 characters; passwords 8–1024 characters. Username and email must be unique across accounts (409 Username already taken / Email already in use). Invalid fields answer 400; an unknown id 404 User not found. Every change is a users security event.

Out-of-range stored values are clamped on read.

wrapUpNudge needs runTimeLimit or runBudget: once a run has used wrapUpPercent % of whichever is further along (time, USD or tokens; below 100 %), the agent is steered once to stop starting new work, finish or pause the current step, verify and write its summary with its Report, and the run log gets Wrap-up nudge: <P>% of the run time limit|run budget used (<detail>); asked the agent to finish up. subagentLimits and contextCompaction apply to runs started after saving, through the run's omp --config overlay: task.maxConcurrency (the run's fair share of this machine: 2 subagents per core and one per 192 MB of free memory beyond the 10% reserve, divided by the card agents running here, capped at subagentMaxConcurrency, at least 1; runs on cluster nodes get subagentMaxConcurrency), task.maxRecursionDepth (subagentMaxDepth), task.maxRuntimeMs (subagentTimeoutMinutes, left out at 0) and compaction.thresholdPercent (contextCompactPercent). The run log shows Subagents: up to N at once, depth D, M min each and Context compaction at P %.

AI provider values (/settings/ai-providers) live in the settings table under ai_providers, each sealed with the credentials encryption key (AES-256-GCM, CREDENTIALS_KEY or DATA_DIR/credentials.key, see Credentials); plaintext is never stored or logged and secret values are only returned masked. A saved value overrides the same environment variable inherited from the server's environment for every omp child process, applied at boot and on every save, so new keys work for the next agent without a restart. A value that can no longer be decrypted (the key changed) is reported as broken and the provider as error until it is entered again.

OAuth sign-ins (/settings/ai-providers/oauth) keep nothing in OMP-UI: omp login stores and refreshes the tokens in omp's own credential store (~/.omp, mounted read-write in Docker), which every omp child reads, so a sign-in applies to the next agent run. It shows up as the provider's ompSignIn (reported by omp usage) and its models: a catalog provider's modelProviders include the omp providers its sign-ins add (openai-codex for OpenAI; google-gemini-cli and google-antigravity for Google). Signing out is omp's /logout.

Scheduled data cleanup runs the OMP-UI-data cleanups of /stats/maintenance (orphan-card-files, orphan-board-files, orphan-workspaces, run-configs, drafts, diff-cache, rotated-logs, database; Docker prunes stay manual) on the server: about a minute after start and then hourly it checks whether one period (7 days weekly, 30 days monthly) has passed since the later of the last run (manual or scheduled) and the moment the schedule was chosen, so enabling a schedule never cleans right away. The last outcome is kept in the settings table under cleanup_state.

#Data transfer

Settings → Data transfer (admin only) moves a server to another machine. An export is a .tar.gz holding manifest.json ({ format: "omp-ui-data", version: 1, appVersion, createdAt, driver, counts, credentialsKey: "file"|"env"|"none" }), db/<table>.jsonl for every table (settings, users with password hashes, boards, tasks, comments, runs, run_events, schedulers, scheduler_runs) as driver-independent domain records (the same shapes the API returns; an export from one database driver imports into another), files/ (DATA_DIR/files) and credentials.key (left out when CREDENTIALS_KEY sets the key). Project folders and omp's ~/.omp are not included.

Method Path Response
GET /data-transfer DataTransferStatus: { driver, users, projects, cards, schedulers, filesBytes, credentialsKey: "env"|"file", activeAgents, importing, backups: { name, size, createdAt }[] }
GET /data-transfer/export The export as application/gzip (omp-ui-data-<yyyymmdd-hhmmss>.tar.gz), built before the response starts. Logged as a security event
POST /data-transfer/import?confirm=replace Raw .tar.gz body → DataImportResult { source: { appVersion, createdAt, driver }, counts, skipped, files, credentialsKey: "restored"|"ignored"|"set-env"|"none", interrupted, backup, signedOut }. Replaces all data: saves the current data to DATA_DIR/backups/before-import-<stamp>.tar.gz (newest 3 kept), replaces every table (one transaction on SQLite and PostgreSQL; MongoDB restores the backup when it fails midway), then DATA_DIR/files and credentials.key, and reloads the token secret, AI provider keys, MCP env and chat bots without a restart. Cards whose agent was running in the source fail with a note (Resume continues them), queued ones go idle, running runs end aborted; rows whose project, card, run or scheduler is missing are left out (skipped). signedOut: the caller's token no longer works (the import replaced the accounts or the token secret). 400 without confirm=replace, for anything but a valid export (wrong format, newer version, row counts not matching the manifest, links or special files in it, no active admin account) — nothing changes then; 409 while agents run or queue, or during another import
GET /data-transfer/backups/{name} Download a pre-import backup (an export; importing it restores that state). 404 for unknown names

A missing key or a failed request simply omits the entry — it never fails the request.

#Git buttons (Push to main / Push to current branch / Create PR)

All act on every project folder (workdir + extraFolders), or only on folders (each must be one of the project folders), one folder at a time. A failure in one folder doesn't stop the others; each folder gets a GitRepoActionResult.

  • 409 while the task's agent is queued or running (“Wait for the agent to finish first.”). 400 if none of the folders is a git repository.
  • Folders that are not git repositories, or have nothing to commit or push, are returned with skipped: true.
  • Push to main: fetches origin/<pushBranch>, commits uncommitted changes if any (git add -A, message = message or the task title), merges origin/<pushBranch> into HEAD (git merge --no-edit; the pull that keeps a remote which moved on from rejecting the push), then git push origin HEAD:refs/heads/<pushBranch> with the board's pushBranch (default main), creating that branch on origin if it doesn't exist; the result's branch and the comment name it. url links to the pushed commit on GitHub/GitLab, otherwise to the repository page. A conflicting merge is aborted (the folder is left as it was) and that folder's error explains it and suggests Create PR; a protected branch likewise. When at least one folder was pushed and none failed, the task's pushedAt is set to now (the UI strikes through the card's title).
  • Push to current branch: same as Push to main, but each folder targets the branch it is currently on (git push origin HEAD:refs/heads/<that branch>), created on origin if missing (before the push, that same branch's origin counterpart is merged in); a folder on a detached HEAD has no current branch and reports an error. pushedAt is set only when every folder landed on the board's pushBranch.
  • Create PR: builds the PR branch omp/<task-slug>-<random> without touching the folder's checked-out branch, index or working tree: it fetches the repo's default branch (the project's Board.defaultBranches entry for that folder, else origin/HEAD, falling back to main/master, then main; the board's pushBranch is not used; it must exist on origin or locally, else the folder's result carries an error), replays only the card's own changes on top of it as one commit (message = PR title), pushes that commit as refs/heads/<branch>, then opens a PR with gh (GitHub) or an MR with glab (GitLab) against that default branch. The card's own changes are the start→end differences of its runs in that folder: each run stores a tree snapshot of every git project folder when it starts and when it ends as commits under refs/omp-ui/task-runs/<taskId>/<runKey>/{start,end} (a run without a recorded end lasts until the next run starts, or until now); they are removed with the card. Changes made by the user or other cards outside the card's runs stay out. A folder where the card has no recorded run reports an error (“no record of what this card changed here”); one whose changes don't apply on the default branch (they depend on commits that aren't there) or leave the default branch's tree unchanged is reported as an error or skipped respectively. PR title defaults to the task title; body defaults to a compact description (lib/pr-body.ts): the latest agent summary's prose (without its ## Report section and OMP-UI-relative images/links, clipped to 1500 chars), its Outcome/Tests/Changes lines as bullets, the task description collapsed in <details> (clipped to 2000 chars; shown plainly when there is no summary), then “Created from OMP-UI”. Without the CLI (or if it fails, e.g. not signed in), the branch is still pushed and url is the provider's “new pull request” page, so the user can open it with one tap.
  • If no identity is configured for git on the server, commits are made as OMP-UI <omp-ui@localhost>.
  • Afterwards one resolved agent comment summarising the result in plain language (with links) is posted on the task and returned as comment; comment.added and task.updated are published.

#Agent rules

  • Move a card to In progress (PATCH status) → omp agent starts in the board workdir (when the board has autoRun; otherwise call POST /tasks/:id/run).
  • The web UI creates new cards on autoRun boards with status: "in_progress", so they start right away (unless the user opts out). API clients choose status themselves; the default is still todo.
  • Agent finishes successfully → its final message is posted as an agent comment, every open feedback comment included in the run is auto-resolved, and the card moves to Done. If that message asks the user something, the question is stored on task.question (cleared when the next run starts or via PATCH question: null); the web UI shows it on the card and lets the user answer with one click.
  • Agent fails → card stays in In progress with agentState: "error" and an agent comment explaining the error. With autoRetry on, the run is retried automatically in the same omp session. Quota errors (agentError matching quota, usage limit, rate limit, 429, too many requests, resource exhausted, insufficient_quota, credit balance or out of credits) wait 5, 10, 15, 30 min, then 60 min for every later retry; other errors wait 15 s, 30 s, 1 min, 2 min, 4 min … (at most 10 min apart). With persistentRetry on (default) a failed run is always retried, whatever maxAutoRetries is, until the card is Done or stopped; with it off, retries stop once task.autoRetries (retries used) reaches maxAutoRetries. task.autoRetries counts retries either way; task.retryAt is when the next one starts (null when none is scheduled). A success, POST /tasks/:id/run or a feedback comment resets autoRetries to 0; Stop or moving the card out of In progress cancels a pending retry. The UI shows such a card as Waiting for quota when its agentError is a quota error, else Retrying.
  • Server restart (boot recovery, on the first API call — the supervisor's health probe makes that immediate): runs left running are marked aborted; queued cards are queued again; with autoRetry on, cards that were running and failed In progress cards resume (each using one retry, bounded by maxAutoRetries even with persistentRetry on, so a card whose run keeps taking the server down stops once its budget is used up) and pending retries keep their retryAt. With autoRetry off, cards that were running end with agentError: "Interrupted by server restart".
  • Agent updates its todo list (omp todo tool) → task.todos (TodoPhase[]: { name, tasks: { content, status: "pending" | "in_progress" | "completed" | "abandoned", startedAt?, completedAt? }[] }) is replaced with the latest list and task.updated is published. The server stamps startedAt (first seen in progress during the current run; an item completed without being seen in progress gets the run's previous list update) and completedAt (first seen completed), carried across updates by item content; while the agent runs, cards show the remaining-time estimate these give (completed items' working time per item × items left); the list stays after the run ends and is [] until the agent keeps one. Read-only: PATCH ignores it. The todo phases are whatever omp names them; OMP-UI imposes no workflow on them.
  • Comment on a Done card (or an idle In-progress card) → card reopens to In progress and the agent resumes the same omp session with the feedback.
  • Comment while the agent is running → feedback is steered into the live session right away as an RPC prompt with streamingBehavior: "steer", exactly like typing into omp mid-run: the user's text goes in word for word (so magic keywords such as orchestrate apply; a message from another card's agent is introduced with its sender and its keywords are neutralized). The live, not persisted SSE event comment.steer { commentId, taskId, boardId, state } reports what became of it: sent (omp took it; it reaches the agent at its next step), delivered (it left omp's steering queue, or the turn it joined ended), deferred (the run was wrapping up or omp declined it; the next run picks it up). The card's Activity chat shows it under the comment.
  • Move to To do/Done manually while running → agent is stopped.
  • The web UI never sets an arbitrary status: cards move by themselves as their agent works, and the only status-affecting controls are its quick actions — Start/Resume/Retry = POST /tasks/:id/run, Stop = POST /tasks/:id/stop, Revert to To do = PATCH /tasks/:id with { status: "todo" }. Done cards not pushed yet also get Push to main = POST /tasks/:id/git/push (no status change). Dragging in the UI only reorders within a column (PATCH position). API clients can still PATCH any status.
  • Task artifact cleanup: a convention of the repo's AGENTS.md, not a prompt: OMP-UI adds nothing to the agent's prompt. The server deletes no files itself; Docker resources marked for the card (label omp-ui.task=<taskId> or compose project task-<taskId>; containers inherit the labels of a marked image they start from) are removed by removeTaskDockerResources (lib/docker.ts) when a run moves the card to Done and, in the background (queueTaskDockerCleanup), when the card or its project is deleted. Policy: TASK-CLEANUP.md.

#Workspaces, files, browser and collaboration

  • Shared project folders: every card's agent runs in the project's folders (workdir + extraFolders) on the branch checked out there. Before the agent starts and after each run, a tree snapshot of every git folder is recorded (lib/server/task-changes.ts) to tell the card's changes from the user's and other cards'; the agent is told to stay on the checked-out branch.
  • Files: every run gets the card's folder (DATA_DIR/files/tasks/<taskId>) and the board's (DATA_DIR/files/boards/<boardId>) as --add-dir. files.updated is published on upload/delete and when a run ends.
  • Browser control (AppSettings.browser: off · headless · visible · relay): written to a per-run omp config overlay (--config); screenshots go to the card's screenshots/ folder.

#Terminal

One persistent, server-wide shell session for the /terminal page, with tmux-like semantics: commands keep running when the browser leaves /terminal and even across an app restart; revisiting re-attaches and replays every block with its output. Types and limits are in lib/terminal-types.ts; the session manager is lib/server/terminal.ts.

Each command is its own /bin/bash -c process (/bin/sh without bash), detached in its own process group, run as the server user with the server's environment minus OMP-UI's secrets (ADMIN_PASSWORD, AUTH_SECRET, database URLs, OMP_UI_*), plus TERM=xterm-256color, COLUMNS=120, PAGER=cat and GIT_PAGER=cat. stdin is empty, so interactive programs see end of input. stdout and stderr go to one log file, interleaved as written.

Method Path Body Response
GET /terminal/stream – 200 text/event-stream (below)
POST /terminal/execute TerminalExecuteRequest: { command, cwd? }. command: non-empty, at most 16384 chars; cwd: an absolute path to an existing directory (default: the session cwd) 201 TerminalBlock (status: "running"). 400 for an empty or too long command, or "Directory not found: <cwd>" for a relative or missing cwd; 429 when 8 commands are already running
POST /terminal/cancel { id } { ok: true }. Kills the block's process group: SIGTERM, then SIGKILL 2 s later. 404 for an unknown id; a finished block is a no-op
DELETE /terminal/session – { ok: true }. Removes finished blocks and their logs; running blocks stay. Every stream receives a fresh snapshot

The stream's unnamed messages are data: <TerminalStreamEvent JSON>\n\n:

  • snapshot (first frame of every connection, and after a clear): { cwd, home, blocks, output, skipped }. blocks oldest first; output[id] is each block's output so far, at most its last 512 KiB (skipped[id] = bytes dropped from the start). Live events continue exactly where the snapshot ends, so a client replaces its state with every snapshot and never refetches.
  • block ({ block, cwd }): a block was added or changed (started, cancelled, timed out, truncated, finished); upsert by id. cwd is the session cwd.
  • output ({ id, data }): new UTF-8 output of a running block, in order.
  • A named ping event (empty data) every 15 s, so clients can detect a silent connection and reconnect.

TerminalBlock: { id, command, cwd, startedAt, pid, status, exitCode, signal, durationMs, timedOut, truncated, cancelled, outputBytes, endCwd, error? }. exitCode is null when the command was killed by a signal (signal, e.g. "SIGTERM"), never started (error says why) or vanished without reporting (error: "lost", e.g. killed with SIGKILL while the server was down).

  • cd persists: a block's endCwd is the directory it ended in (also after exit N); the most recently finished block's endCwd becomes the session cwd, where the next command without cwd starts.
  • Persistence: everything lives in DATA_DIR/terminal/ (mode 0700): session.json (session cwd and blocks, replaced atomically on every change) and per block <id>.log (output), <id>.cwd and <id>.exit (written by the shell when it ends). A restarted server reloads the session, resumes streaming the commands that are still running and finalizes those that ended meanwhile. Stopping the server does not stop the commands.
  • Limits: a command is killed after 6 hours (timedOut: true); a log is served up to 8 MiB, past that the command is killed and the rest is not served (truncated: true). The 100 most recent finished blocks are kept, older ones are deleted with their files.
  • Background jobs (cmd &) keep running after the command ends, but their later output is not served once the block is done.

#Credentials

Keys and tokens for MCP servers and connector services, saved through the MCP connect dialog (there is no separate page). Types are in lib/credential-types.ts; provider templates (fields, validation patterns, MCP launch config, health check) in lib/credential-providers.ts. Records live in the database settings (credentials, plus read/dismissed notification ids in credential_notifications). Secret fields are encrypted with AES-256-GCM under CREDENTIALS_KEY (any non-empty string, hashed with SHA-256) or else a generated DATA_DIR/credentials.key, and are only ever returned masked (abcd••••wxyz, or •••••••• under 12 characters). With a different key, stored secrets cannot be decrypted: those credentials turn failing ("Cannot decrypt: the encryption key changed") until their secrets are entered again.

Credentials belong to the user who created them (CredentialSummary.userId; credentials from before the multi-user upgrade belong to the first admin). Regular users list, read, change, test and get notifications for their own only; another user's id answers 404 Credential not found. Admins see every credential. Background health checks and the MCP environment of every agent use all credentials regardless of owner.

Errors: invalid fields answer 400 { error, fields: CredentialValidationErrors } (error is the first message; fields maps field keys, name and expiresAt to messages); an unknown provider or notification action 400 { error }; an unknown id 404 { error }; a conflicting concurrent edit 409 { error }.

#MCP servers

MCP servers OMP-UI connects to every agent it starts (the /mcp page). Types are in lib/mcp-types.ts, the curated catalog in lib/mcp-catalog.ts; logic in lib/server/mcp.ts. Each connected server is a catalog credential provider with an MCP launch spec plus a saved credential of that provider, written as one entry under mcpServers in omp's user MCP config: <omp agent dir>/mcp.json (the agent dir omp config path reports, see OMP config). OMP-UI's own record of each server (name, provider, credential, enabled, last probe) lives in the database settings (mcp_servers). Every write keeps the file's other entries and top-level keys verbatim (servers added by hand, /mcp add, other tools), adds $schema when missing, and replaces the file atomically; an unparsable file is never overwritten. Entries OMP-UI did not write are listed under external, read-only.

Secrets never reach mcp.json: an entry references them as ${OMPUI_MCP_<SERVER>_<FIELD>} placeholders (server name upper-cased with every other character as _, field key in UPPER_SNAKE_CASE: server my-server, field token → ${OMPUI_MCP_MY_SERVER_TOKEN}), which omp expands from its environment when it loads the file; non-secret values (URLs, regions, …) are inlined. OMP-UI decrypts the values into the environment of every omp process it starts (card runs, chat, helpers, the in-app terminal), so its agents get the server's tools as mcp__<server>_<tool> (omp turns other characters of the server name into _: server my-server → mcp__my_server_<tool>). omp sessions started outside OMP-UI read the same file but do not get these variables, so the servers' secrets are missing there. Editing or deleting a credential (PATCH/DELETE /credentials/:id) re-syncs mcp.json and the agents' environment: a server whose credential is deleted stays in the file with enabled: false.

Errors: invalid fields of a new credential answer 400 { error, fields } as for POST /credentials; an invalid body, server name or provider without an MCP launch spec 400 { error }; an unknown server or credentialId 404 { error }; a server name already used in mcp.json (by OMP-UI or not) 409 { error }; mcp.json that cannot be read, parsed or written (omp not found, invalid JSON) 502 { error }, leaving the file untouched and saving no new credential.

  • SchedulerChatEvent = { type: "activity", text } (progress lines) … then exactly one { type: "done", reply, draft } or { type: "error", error }. draft is the last SchedulerDraft proposed this turn, null when the assistant only answered (e.g. asked a question). SchedulerDraft = { boardId, name, prompt, cron, timezone, enabled, maxRuns, model }, the exact POST /schedulers body to create it.
  • SchedulerLogEntry = { at, kind: "scheduler"\|"status"\|"text"\|"tool"\|"error", text, schedulerRunId, taskId, runId }. runId is the card's agent run (null on scheduler lines).
  • Cron syntax: exactly 5 space-separated fields: minute 0-59, hour 0-23, day of month 1-31, month 1-12 or JAN–DEC, day of week 0-7 (0 and 7 are Sunday) or SUN–SAT; names are case-insensitive. Each field takes *, n, ranges a-b, steps */n, a-b/n and a/n (from a to the field's maximum), and comma lists of these. Macros: @yearly (= @annually), @monthly, @weekly, @daily (= @midnight), @hourly. ?, L, W, # and @reboot are rejected (400). As in Vixie cron, when both day of month and day of week are restricted (neither starts with *), a day matches when either matches (0 9 1 * MON = the 1st of the month and every Monday).
  • Time zone: the expression is evaluated in the scheduler's wall-clock time (timezone, e.g. "Europe/Berlin"), so 0 9 * * * fires at 09:00 local time all year round. Across DST changes: a wall-clock time skipped by the spring-forward jump does not fire that day (it is not moved to another instant); a time repeated by the fall-back hour fires once, at its first occurrence. Each wall-clock minute fires at most once.
  • Due check: the server checks every 30 s (first about 10 s after it starts) and fires each enabled scheduler whose nextRunAt has passed. Before creating the card it saves the next fire time after now, so a slot never fires twice, even across overlapping checks or a crash. Slots missed while the server was down fire once on catch-up (scheduledFor = the first missed slot), then the schedule continues from now.
  • Run limit: after the run that makes runCount reach maxRuns (scheduled or manual), the scheduler disables itself (enabled: false, nextRunAt: null). Re-enabling it needs a higher maxRuns or maxRuns: null.
  • Failures: a missing project ("Project not found") or an error while creating the card records a failed run with its error and sets lastStatus/lastError; the schedule continues.
  • Events: every create, edit and run publishes scheduler.updated ({ scheduler }); deleting publishes scheduler.deleted ({ schedulerId, boardId }). The cards it creates publish the usual task.updated events.

#Live updates

GET /events?boardId=<id> – Server-Sent Events. Each message: data: <ServerEvent JSON>\n\n. Omit boardId to receive everything the caller can see (regular users: events of their own projects only); queue.updated is sent on every stream (for regular users, reduced to their own cards). A named ping event (event: ping\ndata:\n\n, not delivered to onmessage) is sent every 20 s so clients can detect a silent connection and reconnect. The stream closes within one heartbeat when the session is revoked or the user is deactivated, deleted or changes role.

Run events of kind agent hold a JSON SubagentSnapshot (one subagent of an orchestrated run); the latest per id is its state. They are written when a subagent appears, changes status or reports, and when the run ends (subagents still working are marked aborted). Progress in between is sent only live as run.agent.

Task.resources (AgentResources | null) is the memory and CPU of the card's latest agent run: its omp process plus every process it started, as { memoryBytes, peakMemoryBytes, cpuPercent, cpuSeconds, sampledAt } (cpuPercent is percent of one core since the previous sample; cpuSeconds the CPU time since the run started). While a run is going it is sampled every 5 s and sent only live as run.resources ({ runId, taskId, boardId, resources }); the last sample is stored on the card when the run ends (with a task.updated), and the field is cleared when the next run starts. null when the card never ran or sampling is unsupported (Windows). Read-only: PATCH ignores it.

Task.usage (TaskUsage | null) is the estimated model spend of the card's omp session over all its runs: { costUsd, totalTokens, inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, requests, updatedAt }. It is summed from the usage omp records on every model response in the session files (lib/agent/session-usage.ts): the card's session JSONL (assistant messages and model_usage side requests) plus every subagent's JSONL in the session's artifact directory, so context compaction and async subagents don't lose spend. costUsd is omp's estimate at the models' list prices; totalTokens is omp's totalTokens (input + output + cache read + cache write). While a run goes it is rescanned at most every 15 s (incrementally) and stored when it changed, then once more when the run ends, each time with a task.updated; a patch that only sets usage leaves updatedAt unchanged. When a run starts a new omp session, the earlier session's stored spend carries over. At boot, finished cards with a session but no stored usage are tallied once in the background. null until the card's session made a model request. Read-only: PATCH ignores it.
